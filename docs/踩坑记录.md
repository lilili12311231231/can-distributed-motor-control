## 第一部分：CANopen 对象字典与 PDO

### 1.1 R/T 方向按"从机视角"写反了

- **现象**：对象字典挂在 **F407 主节点**上，但 `0x2000` 目标转速写成了 `ODA_RPDO`、`0x2001` 实际转速写成了 `ODA_TPDO`，方向整体反了。
- **根因**：`R` = Receive（收）、`T` = Transmit（发），但"收/发"是**相对于节点自己**说的。对象字典在主节点上，就要用**主节点视角**：

| 对象 | 谁发出 | 主节点视角 | 正确属性 |
|---|---|---|---|
| `0x2000` 目标转速 | F407 发出 → F103 | **T**PDO | `ODA_TPDO` |
| `0x2001` 实际转速 | F103 发出 → F407 收 | **R**PDO | `ODA_RPDO` |

- **解决**：两个对象的 attribute 对调。「收件箱/发件箱」的比喻比较有效——每个节点都有自己的收件箱（RPDO）和发件箱（TPDO），讨论方向前先说清"从谁的门口看"。
- **一句话**：**R/T 是节点视角不是数据流向的绝对方向；对象字典装在哪个节点，就用那个节点的视角写。**

### 1.2 `syncWas` 是第二个参数，不是第三个

- **现象**：主循环里 `CO_process_RPDO/TPDO` 的第二个参数传了 `false`，编译不报错，但 SYNC 同步行为不对。
- **根因**：这两个函数的签名是 `(CO, syncWas, timeDifference_us, timerNext_us)`，`syncWas` 在**第二位**。
- **正确写法**：

```c
bool_t syncWas;
CO_process(CO, false, 1000, NULL);
syncWas = CO_process_SYNC(CO, 1000, NULL);
CO_process_RPDO(CO, syncWas, 1000, NULL);
CO_process_TPDO(CO, syncWas, 1000, NULL);
```

- **一句话**：**协议栈函数参数多且类型相近时，光看编译通过没用——`bool_t` 和指针互换都能编过，必须对着函数签名逐个核对。**

### 1.3 `OD.c` / `OD.h` 是自动生成的，手改要三处同步

- **现象**：文件头明确写着 `DON'T EDIT THIS FILE MANUALLY`，但可选路径只有两条——用 CANopenEditor 重新生成，或手写改。
- **根因**：CANopenNode v4.0 的对象字典是**三层结构**，改一个对象要同时改三层，漏一层就会出现"能编译、运行不对"：

| 层 | 文件 | 改什么 |
|---|---|---|
| ① 数据变量 | `OD.h` 的 `OD_RAM_t` / `OD.c` 的数据初始化 | 声明变量 + 赋初值 |
| ② 对象绑定 | `OD.c` 的 `ODObjs_t` / `ODObjs` | 指向数据、设 attribute、设 dataLength |
| ③ 对象列表 | `OD.c` 的 `ODList` | 加一条 entry（`{index, subIndex, &obj}`），哨兵 `{0x0000,...}` 必须在最后 |

- **一句话**：**自动生成的文件一旦手改，就等于接管了生成器的职责——三处必须同步，改完要拿"读对象字典"的方式验证，不能只看编译结果。**

### 1.4 attribute 写错：只读对象写成了可读写

- **现象**：`0x2001` 实际转速（从站上报，主站只读）写成了 `ODA_SDO_RW`。
- **根因**：`ODA_SDO_RW` = SDO 可读可写；`ODA_SDO_R` = 只读。语义上主站不该能改从站上报的实测值。
- **解决**：改成 `ODA_SDO_R | ODA_RPDO | ODA_MB`。
- **一句话**：**attribute 不是"能不能用"，而是"谁能怎么用"——只读对象写成可写，等于给自己留了个改坏数据的口子。**

### 1.5 `OD_RAM` 初始化时漏了逗号

- **现象**：加两个变量后编译报错，指向结构体初始化位置。
- **根因**：C 结构体初始化列表里，上一个字段的 `}` 后面必须补逗号，加字段时最容易漏。
- **一句话**：**在结构体初始化列表里加字段，"逗号 + 结尾哨兵"是两个固定检查点。**

### 1.6 COB-ID 的 bit31 / bit30 语义

- **现象**：对着 `0x40000181` 和 `0x00000201` 两个值看不出规律。
- **根因**：COB-ID 是 32 位，**高 3 位是标志位**，低 11 位才是真正的 ID：

| 位 | 含义 |
|---|---|
| bit31 | **有效/启用**（1 = 有效，0 = 该 PDO 停用） |
| bit30 | 不允许 RTR（1 = 禁止远程帧请求） |
| bit29 | 帧格式（0 = 11 位标准帧） |
| bit10~0 | 实际 CAN ID |

所以 `0x40000181` = 启用 + 不允许 RTR + ID 0x181；`0x00000201` = 启用 + ID 0x201。
"8 或 C 开头 = 停用"这个经验法则就是这么来的：bit31 = 0 时最高位落到 8/0。

- **一句话**：**CANopen 里出现"看起来像 ID 但高 3 位很怪"的数，先拆标志位再看 ID。**

### 1.7 应用对象必须落在制造商专用区

- **约束**：自定义对象索引应放在 **0x2000 ~ 0x5FFF**（制造商专用区），不要去占 0x1000~0x1FFF 的通信参数/设备参数区。
- **一句话**：**对象字典的地址段是标准划分的，占错区会和协议栈自己的对象打架。**

## 第二部分：SERVO42C 串口与 CAN 实现的硬约束

### 2.1 上电必须先切到 CR_UART 模式

- **约束**：SERVO42C 出厂默认是**脉冲/方向模式**，串口位移指令（0xFD）不会生效。
- **做法**：初始化第一步发 `0x82 = 0x02`（CR_UART 串口控制模式），然后**等约 2 秒**让驱动器完成模式切换。
- **原因**：模式切换是驱动器内部状态机，不等它切完就发运动指令，指令会被丢弃或行为异常。

### 2.2 发指令前必须清空接收缓冲

- **约束**：0xFD 位移指令驱动器会回一条"到达/确认"，残余字节会留在 UART 接收缓冲里。
- **做法**：每次发指令前后都做一次「非阻塞读空」：

```c
while (HAL_UART_Receive(&huart1, &flush_tmp, 1, 5) == HAL_OK) {}
```

- **原因**：不清空的话，下一次读编码器时会把上一条指令的应答当成帧数据，导致解析错位。

### 2.3 读编码器不能假设首字节就是帧头

- **约束**：驱动器回复 8 字节 `E0 + carry(4B) + value(2B) + 校验(1B)`，但缓冲里可能混有残留字节。
- **做法**：逐字节找 `0xE0`，找到后再一次性读剩余 7 字节；同时用 `HAL_GetTick()` 做 200 ms 超时：

```c
while (1) {
    if (HAL_UART_Receive(&huart1, &b, 1, 10) == HAL_OK && b == SERVO_ADDR) { rx[0] = b; break; }
    if (HAL_GetTick() - t0 > 200) return -1;      // 超时返回错误码，不返回 0
}
```

- **原因**：超时时返回 `-1` 而不是 `0`，调用方才能区分"位置真的是 0"和"读取失败"。

### 2.4 校验是和校验（低 8 位），不是 CRC

- **约束**：SERVO42C 用**所有字节求和取低 8 位**作为校验字节，与 Modbus 的 CRC16 完全不同。
- **做法**：发送时累加地址 + 功能码 + 数据；接收时对前 7 字节累加，与第 8 字节比较，不一致直接返回 `-1`。
- **一句话**：**换一种设备就换一套校验规则，别把 Modbus 的 CRC 习惯带过来。**

### 2.5 方向与幅值必须拆开发

- **约束**：0xFD 指令的 `dir` 占 **bit7**、`speed` 占低 7 位，而 `step` 是独立的 4 字节**无符号**量。
- **做法**：先算带符号的差值，负数时把方向置 0 并取绝对值：

```c
int32_t delta_step = delta_enc * 25 / 512;
uint8_t dir = 1;                                          // 1 = 正转
if (delta_step < 0) { dir = 0; delta_step = -delta_step; } // 0 = 反转
Servo_SetPosition(dir, 10, delta_step);                    // speed = 10 → 5000 步/秒
```

- **原因**：`step` 字段没有符号位，把负数直接塞进去会被解释成一个巨大的正数，电机直接冲出去。

### 2.6 carry 会过期，所以用"回零 + 相对偏移"

- **约束**：编码器多圈位置 = `carry × 65536 + value`，`carry` 存在驱动器 EEPROM 里，**只有通电转动才更新**。断电后手拧电机，`carry` 就与真实位置不符。
- **做法**：不依赖 `carry` 的绝对值，上电后由人工对零并按键确认，记录 `home_full`，之后所有目标都用相对 `home_full` 的偏移表示。
- **一句话**：**绝对编码器的"绝对"只在通电期间成立；跨上电周期要用参考点重建坐标。**

### 2.7 主站要"单发"，不能高频重发

- **约束**：从站收到目标后要等电机走完（约 500 ms），期间主循环被阻塞。
- **做法**：主站每 3 秒切换一次目标，且**切换时才发一帧**，不周期连发。
- **原因**：高频重发会让从站在运动中途收到新目标，表现为"走一半又折返"。

### 2.8 中断里只置标志，不做耗时动作

- **约束**：读一次编码器涉及串口收发 + 200 ms 超时，绝不能放在 CAN 接收中断里。
- **做法**：`HAL_CAN_RxFifo0MsgPendingCallback` 里只解析 4 字节、置 `new_target_flag`，动作全部交给主循环。
- **一句话**：**中断服务函数的长度以微秒计，任何带等待的动作都应该退化成"置标志"。**

## 第三部分：工程文件

### 3.1 源码是 GBK，推到 GitHub 中文注释全变成问号

- **现象**：Keil 里注释正常，在 GitHub 网页点开 `main.c`，所有中文都是 `����`；下载下来用 VS Code 打开也是同样的乱码。
- **根因**：Keil MDK 在中文 Windows 上新建文件默认按 ANSI 存（即 GBK），而 GitHub / VS Code 一律按 UTF-8 解码。同一个字节序列，两套编码，注释就崩了。
- **做法**：把工程里的 `.c/.h` 统一转成 UTF-8（**不带 BOM**）。转换时逐文件核对：先按 GBK 解码得到原文，写出 UTF-8，再读回来比对字符串是否完全一致、行数是否未变 —— 只改编码，不动任何一个字节的代码。
- **Keil 侧**：转换后如果 Keil 显示乱码，在 `Edit → Configuration → Editor → Encoding` 里选 `UTF-8`（老版本可能只有 `Encode in UTF-8 without signature`）。编码只影响注释显示，不影响编译。
- **一句话**：**注释乱码不是"显示问题"，是别人第一眼就会看到的东西；仓库面向网页阅读时，源码编码要和平台一致。**

## 附：这套项目的排查顺序

1. **先确认链路，再确认协议**：CAN 有没有 ACK（示波器/回环模式）→ 帧 ID 对不对（滤波器）→ 数据字节序对不对。
2. **先确认驱动器状态，再发运动指令**：模式是否切对 → 是否使能 → 再谈位置。
3. **读数据时永远先做帧头对齐 + 校验**：不定长/带应答的串口协议，不能假设"读 8 字节就是 8 字节有效数据"。
